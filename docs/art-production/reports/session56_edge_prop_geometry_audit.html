Headline finding

The runtime's own math decomposes cleanly into two independent variables — a fact the old single-ratio heuristic could not see. Neither variable was previously named or measured on its own; both were only ever visible as a tangled output (bleed %, intrusion px).

// visible-silhouette height (vb.y1 − vb.y0) as the common denominator: ρ = roadDepthsrc / visHsrc // road-facing overhang, as a fraction of asset height cityFrac = cityDepthsrc / visHsrc // city-facing depth, as a fraction of asset height ratio = ρ + cityFrac // visible W:H — the OLD heuristic's only variable roadIntrusion(h) = ρ · h // governs the 8px hard cap — ratio has NO effect here bleed(h) = max(0, cityFrac·h − 35.4) // governs city-side overflow — no hard cap exists

This formula was not fit to the data — it is edgePlacement(), algebraically rearranged, and it reproduces every number in the Session 53/54/55 changelog entries to two decimal places (81.09px, 5.60px, 40.09px, 4.90px, 41.17px, 7.81px, 0.19px, and the ~49%/~51%/~43% bleed-percentage figures PM reacted to in Session 53 — all recomputed independently below, all matched).

The core answer

Road intrusion is controlled entirely by ρ (road-facing overhang, as % of the asset's own height) — the overall width:height ratio has no bearing on it. The old 0.5–0.6 ratio heuristic was, unknowingly, a bleed-control rule wearing a road-safety costume. That's the exact mechanism behind Session 55: a narrow, low-bleed asset (ratio 0.620) can still carry an oversized ρ (11.16%, vs. 4–8% on every other registered asset) and land at 98% of the intrusion budget.

Plain-English model. Each prop's source PNG carries three alpha-measured rectangles (all in source pixels, alpha ≥ 32): visualBounds (the full silhouette), footprint (ground-contact only — wheels/feet, never the overhanging canopy), and a single pivot point. The pivot is deliberately not the sprite's own center — it sits on the footprint's road-facing edge, at the ground line. That single point is what the runtime anchors to a fixed on-screen coordinate; the entire sprite then scales uniformly around it (one scalar s = heightPx / visHsrc, applied to width and height alike — never a non-uniform stretch, never a mirror).

On screen, the pivot itself never moves once heightPx is fixed — it sits at a constant design-px coordinate derived purely from the road geometry (roadEdgeX ± safetyBuffer), independent of the asset. What moves as heightPx changes is how far the silhouette reaches in either direction from that fixed point, because the scale factor s is the only thing that grows.

Pseudocode (source-faithful, game.js:1163–1234)

s = heightPx / (vb.y1 - vb.y0) // uniform scale, height-driven only pivotX = roadEdgeX + dir * safetyBuffer // FIXED — independent of the asset sx(u) = pivotX + (u - pivot.x) * s // order-preserving; never mirrored roadFacingVisX = (edge=="right") ? vb.x0 : vb.x1 cityFacingVisX = (edge=="right") ? vb.x1 : vb.x0 roadIntrusion = |pivot.x - roadFacingVisX| * s // pure silhouette measure × scale bleed = max(0, (edge=="right") ? sx(vb.x1)-W : -sx(vb.x0)) ok = footprintClear(footprint vs roadEdgeX) AND (roadIntrusion <= intrusionAllow)

How alpha bounds feed in: visualBounds/footprint are measured once, offline, at a fixed alpha ≥ 32 threshold per the repo's own convention (stated inline at every EDGE_PROP_DEFS entry) — the runtime never re-measures alpha. A different threshold would shift vb.x0/x1 and therefore ρ/ratio directly; the formulas below are only as trustworthy as that threshold staying consistent across every future asset.

Bounds convention — two numbers, same underlying measurement

Two different things both get called "the alpha≥32 bounds" in this project, and they are off by ~1px on at least one registered asset: stored runtime bounds — the visualBounds/footprint object literals inside EDGE_PROP_DEFS in game.js, which is what edgePlacement() actually reads — versus literal alpha-pixel bbox — the raw last-opaque-pixel index reported in the asset's metadata JSON notes field at export time.

Confirmed example: right cart v002's metadata JSON records the measured alpha≥32 bbox as (226,431)–(949,1056) (inclusive last-opaque-pixel indices); game.js's EDGE_PROP_DEFS stores visualBounds: {x0:226, y0:432, x1:950, y1:1057} — y0/x1/y1 each shifted by exactly 1px, x0 untouched. That's consistent with an inclusive-index vs. exclusive-upper-bound (width/height) convention difference at export time, not a measurement error — the two production props checked against their own metadata (chai counter v001, left cart v003) show zero drift. Runtime calculations are correct as stored and should not change. Future tooling that re-derives bounds from raw alpha scans should target the game.js-stored convention (exclusive upper bound), not the metadata JSON's inclusive-pixel convention, to avoid silently reproducing this ~1px gap on new assets.

How height/scaling feeds in: everything derived from source-px distances (roadIntrusion, on-screen width, footprint width) scales purely linearly with heightPx, because s is directly proportional to it. bleed does not scale purely linearly — it's affine, because it's measured against the fixed screen constant W − pivotX (35.4px), which does not grow with the asset. This split — one clean-linear quantity, one affine-with-a-fixed-offset quantity — is exactly why ρ alone predicts intrusion risk across scales while bleed needs the full formula.

C Why the Session 55 prototype nearly failed

Not a measurement artifact — a structural property of that specific silhouette, isolated by ρ.

Look at the pivot-normalized position column above: every other registered asset — cart, counter, both prior vertical prototypes — places its pivot within 5–7% (right) / 94–96% (left) of its own visible width, measured from the road-facing edge. The Session 55 prototype's pivot sits at 18.0% — two-and-a-half to three-and-a-half times further in. This percentage is diagnostic, not an authored target — it's useful here for spotting the outlier, but it is not the road-safety rule itself (see §H): the authoritative requirement is that the pivot sit on the honest road-facing ground-contact footprint edge, whatever normalized position that produces for a given silhouette.

That inset is not decorative; it is the geometric quantity roadIntrusion literally measures. Because the pivot is pinned to the footprint's road edge (the wheelbase), and roadIntrusion is the distance from that pivot out to the silhouette's road-facing-most point, a pivot sitting deep inside the silhouette means the service counter/shelf structure reaches a long way road-ward of the wheels before the art runs out. Converted to ρ — the same overhang expressed as a fraction of the asset's total height, independent of overall width — this source measures 11.16%, against 4.3–8.0% for every comparator, including the current production masters.

The causal chain

Narrowing the overall silhouette (going from ratio 0.844 → 0.620) improved cityFrac and killed bleed almost entirely (20.67px → 0.19px) — a genuine, real win. But narrowing a silhouette says nothing about where its road-facing structure sits relative to the wheelbase. This source happened to narrow by trimming city-side bulk while keeping a proportionally large counter overhang on the road side — the two authoring choices are independent, and only one of them was targeted. roadIntrusion = ρ·h is scale-independent of ratio entirely; a narrow asset with a deep road-side overhang is exactly as dangerous as a wide one with the same ρ.

D Derived road- and city-facing envelope

Every number below is read directly off the roadIntrusion(h)=ρ·h / bleed(h)=cityFrac·h−35.4 identities — not chosen by eye.

Road-facing (ρ) — the safety-critical axis

The hard rule is a formula, parameterized by each asset's own declared maximum runtime height — the highest heightPx that asset is ever allowed to run at — not a single universal percentage:

roadIntrusion(h) = ρ × h hard requirement: ρ × declaredMaximumRuntimeHeight ≤ 8px ⇒ ρ_hard-max = 8 / declaredMaximumRuntimeHeight preferred production policy — 30% headroom on the hard cap (the explicit, single headroom policy this contract adopts; every other preferred number below is derived from it, not independently chosen): ⇒ ρ_preferred-max = 0.70 × ρ_hard-max = 5.6 / declaredMaximumRuntimeHeight
8.9% is an example, not a universal constant

The Session 56 draft stated "ρ ≤ 8.9%" as if it were a fixed law. It is not — it is the specific output of the formula above when declaredMaximumRuntimeHeight = 90px, which happens to be the top of the current landmark family's 70–90px stated range:

at declaredMaximumRuntimeHeight = 90px: hard ρ ≤ 8.89% (= 8 / 90) preferred ρ ≤ 6.22% (= 5.6 / 90) at declaredMaximumRuntimeHeight = 120px (hypothetical — e.g. a taller landmark family): hard ρ ≤ 6.67% (= 8 / 120) preferred ρ ≤ 4.67% (= 5.6 / 120)

A future asset family declared to run taller than 90px must recompute its own ceiling from the formula — it may not reuse 8.9%/6.22%. Every asset brief (§H) must state its own declared maximum runtime height for exactly this reason.

Sized against the asset's own declared maximum, not against whatever height a prop happens to run at today. heightPx has already been retuned twice in this project's history (88→80→70, Session 53); an art asset authored to a ρ that's merely safe at its current running height could silently fail a future re-tune upward with zero code change.

City-facing (cityFrac) — a design axis, not a safety one

There is no runtime cap on bleed — ok never checks it. It's PM-judgment territory only, tracked in the changelog as "how much of the sprite runs off the city side," which Session 53 flagged as too high (~58%) and Session 55 flagged the opposite failure mode as untested (0.19px — nobody has PM-reviewed whether near-zero bleed reads as "tucked to the edge" or "floating, disconnected from the city").

zero-bleed threshold: cityFrac = 35.4 / h at h=70: 50.6% at h=80: 44.3% at h=90: 39.3%
cityFrac 55–75% is retracted as a target band

The Session 56 draft proposed cityFrac ≈ 55–75% as a target band, citing "the PM-approved 40–55%-of-onscreen-width bleed range." That justification conflates two different metrics — bleed as a percentage of on-screen width is not the same quantity as cityFrac as a percentage of source height — and the conflation is visible directly in this session's own table (§B): the actual shipped, approved production masters run cityFrac 92.95–109.39%, nowhere near the 55–75% band this draft was about to freeze. A 3-asset production sample (one of which, the chai counter, is a different silhouette family from the two carts) plus 3 prototypes explicitly built to explore the opposite, narrow end of the space is not evidence for a universal band either way.

Status: demoted from target band to measured observation. City-facing depth stays measurable (report cityFrac and projected bleed at the asset's intended height), projected for bleed before art is finalized, and visually PM-reviewed — with no numeric ceiling or band asserted until a larger, more deliberately-sampled measurement set exists. It may turn out to be family-specific (a cart and a counter plausibly do not share one number) rather than universal.

Explicit sizing conflict

The current shipped production right cart (v002) — the reference master, not a prototype — drops to only 10% headroom at 90px. If a future session ever raises the landmark heightPx toward the top of the stated band, the existing right master approaches its own cap with almost no margin, using art that was never authored against this constraint (it predates this analysis). This isn't a defect today — production only runs it at 70px — but it means the "safe reference art" this contract would otherwise point to is itself only safe at the bottom of the intended range.

One geometry cannot cover all three sizes equally well only in the sense that fixed-ρ art loses headroom monotonically as heightPx rises — there's no single ρ value that has "flat" margin across 70→90. But because the relationship is exactly linear and known, a single ρ ceiling sized against the worst case (90px) — as derived in §D — automatically keeps every lower height safer still. The fix is sizing discipline, not three separate rulesets.

F Universal rule vs. asset-family rules

One contract is defensible for everything measured so far. ρ ranges 2.05%–11.16% across this sample, and that spread is driven far more by authoring choice than by physical archetype: the widest ρ spread (2.05% vs. 11.16%) sits within the single "vada-pav cart" family across three different prototypes, wider than the gap between the cart family (7.00–8.00% for production masters) and the chai counter (5.74%). Nothing in the evidence points to carts needing a structurally different ceiling than counters.

What the evidence does not cover: a genuinely wide/deep archetype (a long market stall, a multi-bay landmark) where the road-facing service edge might be structurally unable to sit within 6–9% of total height without misrepresenting the object. No such asset has been measured. Per the brief's own instruction not to invent categories without evidence — recommend one "Tall Edge Prop" contract now, and flag a "Tall Counter/Stall" sub-envelope as a contingency to open only if a future measured asset can't meet it for a real structural reason, not preemptively.

G Status of the old ~0.5–0.6 W:H guidance

Verdict: option 3 — demote to a secondary check

The old heuristic is ratio = ρ + cityFrac with no visibility into the split. It correctly predicts bleed risk (a low ratio at a given pivot position tends toward lower cityFrac, hence less bleed) — that's genuinely why it emerged from Session 53's bleed complaint. It has zero predictive power over road intrusion, which depends on ρ alone; Session 55 is the direct proof, landing at the old heuristic's preferred narrow ratio (0.620) while nearly maxing the intrusion budget.

W:H cannot validate road intrusion. The authoritative road-safety variable is ρ. Keep the old ~0.5–0.6 W:H range as a coarse, secondary visual/composition heuristic ("does this read as tucked to the edge") applied only after ρ has been verified independently — never as a stand-in for road-safety review, and never re-derived upward from the now-retracted cityFrac band (see §D). A wider range (0.6–0.8) is not adopted here — that number depended on the cityFrac 55–75% band this pass retracted.

H Asset-brief template — measurable, per-asset fields

Written for a pipeline that can measure alpha bounds, not judge silhouettes by eye. Every future tall edge-prop brief should declare these fields explicitly, in this order, so the hard formula (§D) can be checked directly against the brief before art is finalized.

Required fields

  1. Target runtime height — the heightPx this asset is expected to actually run at today.
  2. Maximum runtime height — the highest heightPx this asset is declared to ever run at (may equal target height; if a future re-tune is plausible, declare the top of that range — see §D's ρ formula, which is sized against this number, not the target height).
  3. Stored visible bounds — the silhouette bbox as it will be stored in EDGE_PROP_DEFS (game.js convention — see the bounds-convention note in §A), distinct from the literal alpha-pixel bbox an export tool may report.
  4. Footprint / ground-contact pivot — the honest road-facing ground-contact footprint edge. This is the authoritative pivot rule — not a normalized-percentage target. The 5–7% figure discussed in §C is a diagnostic for spotting outliers after the fact, not a value to author toward.
  5. Road-facing depth — the source-px distance from the ground-contact wheelbase's road-facing edge to the silhouette's road-facing-most point (counter lip, canopy corner, whatever extends furthest toward the road).
  6. ρ — road-facing depth ÷ total visible height.
  7. Projected road intrusion at target height and at maximum height — ρ × h evaluated at both declared heights; the maximum-height figure is what's checked against the 8px hard cap (§D).
  8. City-facing depth — source-px distance covering structural mass, storage, canopy overhang, handles on the city-facing side. Measure and report; no fixed target is asserted (§D).
  9. Projected outer bleed — max(0, cityFrac·h − 35.4) at the target height; report so it's a visible decision, not a discovered surprise post-ship (as it was in Session 53).
  10. Preferred road-intrusion headroom — state which headroom policy the brief is authored against (this contract's default: 30% below the hard cap at declared maximum height — see §D).
  11. Acceptable visual/on-screen visibility — a PM sign-off field: does the projected bleed/intrusion combination read correctly on screen at the target height. Human-review, not a computed number.

What is explicitly not a fixed rule here

  • Total visible W:H — falls out of ρ and city-facing depth, but is not itself authored toward, and cannot substitute for checking ρ directly (§G). Use the old ~0.5–0.6 range only as a secondary, non-binding visual/composition check.
  • cityFrac target band — no band is asserted (§D). Measure and project bleed; don't author toward a percentage.
  • Pivot normalized position — diagnostic only (§C); the footprint-edge rule in field 4 above is the real requirement.

I Left/right symmetry
